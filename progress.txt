## Codebase Patterns
- Source `.envrc` directly (`source "/path/.envrc"`) for reliable env var loading in Bash tool (NOT `direnv export bash`)
- Use `uv sync --reinstall` if editable CUA packages fail to import (agent, cua_bench, etc.)
- Solver exits with code 1 on MAX_STEPS_EXCEEDED — expected behavior, not an error
- BaseTool pattern: constructor takes domain object + optional cfg, calls `super().__init__(cfg)`; `@register_tool` sets `cls.name` and adds to `TOOL_REGISTRY`. `_verify_json_format_args` handles both dict and JSON string params.
- CUA trajectory reasoning summaries: `turn_NNN/NNNN_agent_response.json → response.output[].summary[].text`
- Turn count ≠ step count: each turn can contain multiple API calls (~2 steps/turn for openai/computer-use-preview)
- To inject content the agent sees every turn, use the `instructions` param (PromptInstructionsCallback) — it's the only content never truncated. Use for TASK_MEMORY.md.
- `function_call_output` items (tool results) are ephemeral — agent must act on them immediately, they get truncated within a few turns

## 2026-03-07 - CUA context management analysis

- Created `docs/cua-context-management.md` documenting the two-layer truncation system:
  - Layer 1: ImageRetentionCallback (client-side) removes old screenshot triplets (reasoning + computer_call + computer_call_output), keeps only last N images

- Verified from real trajectory data (186-turn Magic Tower run): at turn 100, only 20 items survive — 2 user msgs, 12 message items, 3 computer_call + 3 computer_call_output pairs. Zero reasoning items, zero function_call items.

- Files changed: docs/cua-context-management.md (created), architecture.md (updated), prd.json (updated), progress.txt (updated)
- **Learnings for future iterations:**
  - `message` items survive ImageRetentionCallback because they aren't adjacent to computer_call_output — but they still get API-truncated eventually
  - The `input` field in api_start.json (not `messages`) contains the actual items sent to OpenAI Responses API
