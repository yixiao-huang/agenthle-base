## 1. Golden Reference Deep Comparison

This is the primary focus of the audit. Three golden references were analyzed against the TinyClaw implementation.

### 1.1 OpenClaw `createMemoryGetTool` (memory-tool.ts, lines 101-140)

#### API Shape Comparison

| Aspect | OpenClaw | TinyClaw | Match? |
|--------|----------|----------|--------|
| Tool name | `memory_get` | `memory_get` | OK |
| `path` param | `Type.String()`, required | `type: string`, required | OK |
| `from` param | `Type.Optional(Type.Number())` | `type: integer`, optional | OK (integer is stricter, appropriate) |
| `lines` param | `Type.Optional(Type.Number())` | `type: integer`, optional | OK (integer is stricter, appropriate) |
| Description | "Safe snippet read from MEMORY.md or memory/*.md with optional from/lines..." | "Safe snippet read from MEMORY.md or memory_logs/*.md with optional from/lines..." | OK - adapted path convention for TinyClaw |
| Return format | JSON `{ text, path }` | Plain string (content or error message) | INTENTIONAL deviation - TinyClaw tools return plain strings per BaseTool pattern |

**Assessment**: API shape is a faithful adaptation. Parameter names (`path`, `from`, `lines`) are identical. The `integer` type constraint for `from`/`lines` is actually stricter than OpenClaw's `Number()` which allows floats -- this is appropriate since line numbers should be integers. OpenClaw enforces integer via `readNumberParam(params, "from", { integer: true })` at runtime, while TinyClaw declares it in the schema.

#### Validation Logic Comparison

| Check | OpenClaw | TinyClaw | Match? |
|-------|----------|----------|--------|
| Empty path | `throw new Error("path required")` if `rawPath.trim()` empty | Returns error string if path is empty string (fails `.endswith(".md")` check) | WEAK - different error message path, but functionally covered |
| Path traversal | `path.resolve()` + `path.relative()` check: `!relPath.startsWith("..")` + `!path.isAbsolute(relPath)` | `".." in file_path or file_path.startswith("/")` | See detailed analysis below |
| .md restriction | `absPath.endsWith(".md")` | `file_path.endswith(".md")` | OK |
| Allowed paths | `isMemoryPath(relPath)`: `MEMORY.md`, `memory.md`, or `memory/*` prefix; plus `extraPaths` | No prefix restriction -- any `.md` file within base_dir | INTENTIONAL - see below |
| Missing file | Returns `{ text: "", path: relPath }` | Returns `"File 'X' not found or empty."` | OK - different return convention but helpful messaging |

**Path Traversal Analysis (IMPORTANT)**:

OpenClaw's approach is more robust:
1. Resolves the path to absolute using `path.resolve(workspaceDir, rawPath)`
2. Computes `path.relative(workspaceDir, absPath)`
3. Checks the *resolved* relative path doesn't start with `..` and isn't absolute

TinyClaw uses a simpler string check: `".." in file_path`. This is functionally adequate because:
- It catches `../etc/passwd`, `foo/../../../etc/passwd`, and similar traversals
- Combined with the `.md` extension check, attack surface is limited
- The `MemoryStore.read_file()` method uses `self.base_dir / relative_path` (pathlib join), which correctly sandboxes within base_dir

However, there is a subtle edge case: a filename literally containing `..` (e.g., `notes..summary.md`) would be falsely rejected. This is unlikely in practice but is a difference from OpenClaw which only checks the *resolved* relative path.

**Verdict**: The path traversal check is ADEQUATE but less precise than OpenClaw's canonical approach.

**Path Scope (No `isMemoryPath` equivalent)**:

OpenClaw restricts `readFile` to paths matching `isMemoryPath()`: only `MEMORY.md` or files under `memory/`. TinyClaw does NOT enforce a similar scope restriction -- any `.md` file relative to `base_dir` can be read. This is an INTENTIONAL deviation because TinyClaw's storage layout is different (task-scoped directories, session files, etc.), and all paths within `base_dir` are legitimate memory files. Documented in `docs/memory-system.md` storage layout.

#### Error Handling Comparison

| Scenario | OpenClaw | TinyClaw |
|----------|----------|----------|
| Manager unavailable | Returns `{ path, text: "", disabled: true, error }` | N/A (no manager concept) |
| Exception during read | Catches, returns `{ path, text: "", disabled: true, error: message }` | `MemoryStore.read_file()` catches `OSError`/`UnicodeDecodeError`, returns `""` |
| File missing | Returns `{ text: "", path: relPath }` | Returns human-readable error string |

OpenClaw distinguishes "missing" (empty text, no error) from "error" (disabled: true). TinyClaw merges both into a single "not found or empty" message. This is ADEQUATE for a benchmark agent -- the distinction between missing and empty is less critical.

### 1.2 OpenClaw `readFile` (manager.ts, lines 537-608)

#### Line Range Computation

| Aspect | OpenClaw | TinyClaw |
|--------|----------|----------|
| Split method | `content.split("\n")` | `file_path.read_text().splitlines(keepends=True)` |
| Start line | `Math.max(1, params.from ?? 1)` | `max(0, start_line - 1)` for indexing (1-based input) |
| Line count | `Math.max(1, params.lines ?? lines.length)` | `num_lines` is `None` if not provided (read to end) |
| Slice | `lines.slice(start - 1, start - 1 + count)` | `lines[start_idx:end_idx]` |
| Join | `slice.join("\n")` | `"".join(lines[...])` with `keepends=True` |
| No range given | Returns full `content` (no split) | `start_line=1, end_line=None` (reads all) |

**Notable difference**: OpenClaw forces `lines` to minimum 1 via `Math.max(1, params.lines ?? lines.length)`. TinyClaw's `MemoryGetTool.call()` converts `lines=None` to `end_line=None` (read to end), and if `lines` is provided, computes `end_line = start_line + num_lines - 1`. If `lines=0` were passed, TinyClaw would compute `end_line = start_line - 1`, resulting in an empty slice. OpenClaw would return at least 1 line. This is a MINOR edge case -- `lines=0` is not a realistic input.

**Newline handling**: OpenClaw splits on `\n` and joins with `\n`, potentially losing a trailing newline. TinyClaw uses `splitlines(keepends=True)` and `"".join()`, preserving original line endings. TinyClaw's approach is arguably more correct.

## 3. Code Quality Audit

### Reference Attribution
The class docstring (lines 69-74) correctly attributes the OpenClaw source files and what was adopted. This follows the project's quality requirements.

### Security
- Path traversal: `".." in file_path` -- adequate but less precise than OpenClaw's resolve-then-check approach. See Section 1.1 for details.
- Absolute path check: `file_path.startswith("/")` -- correct.
- `.md` restriction: `file_path.endswith(".md")` -- correct.
- No symlink check: OpenClaw checks `lstat` for symlinks in `extraPaths`. TinyClaw does not, but since all paths are within the controlled `base_dir`, this is acceptable.

### Error Handling
- Missing file returns friendly message (no stack trace).
- Invalid paths return clear error messages.
- `MemoryStore.read_file()` catches `OSError` and `UnicodeDecodeError`.

### Dead Code
None found.

### Test Coverage
9 tests for `MemoryGetTool` (lines 86-137 of test file):
- Registration, schema validation
- Full file read, line range read
- Path traversal rejection, absolute path rejection
- Non-.md rejection, missing file handling
- Log file read, JSON string params

**Missing test cases** (minor):
- `from` without `lines` (read from line N to end)
- `lines=0` edge case
- Empty path string
- Path with `..` embedded but not at start (e.g., `foo/../bar.md`)
