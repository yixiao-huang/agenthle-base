### Overall Assessment

US-OC-037 is a substantial, well-structured piece of work that adds GPT 5.4 `computer` tool support to the CUA OpenAI loop. The format normalization (`_normalize_messages_for_gpt54`) and orphan call repair are implemented correctly and verified on real VMs. However, the normalization approach is a bespoke solution specific to the OpenAI loop — OpenClaw handles cross-model format differences at the session history layer via `sanitizeSessionHistory()`, not per-loop. This design divergence is acceptable for the CUA context but worth noting.

### Design Concerns

1. **Format normalization lives in the wrong layer** (Design Soundness). OpenClaw's `sanitizeSessionHistory()` in `google.ts` runs a 7-pass pipeline on session messages _before_ any provider loop sees them. This means format conversion is centralized and model-agnostic. In CUA, `_normalize_messages_for_gpt54()` runs inside the OpenAI loop's `predict_step()`, meaning:
   - If another loop needs the same conversion, the logic must be duplicated
   - The Anthropic loop handles its own format issues separately (e.g., `computer_20251124` compat)
   - No shared session-history sanitization exists in CUA

   **Concrete fix**: This is an architectural gap in CUA, not a bug in US-OC-037. For now, document the divergence. Long-term, consider a `sanitize_session_items()` callback that runs before any loop's predict_step.

2. **Two separate orphan-repair implementations** (Design Soundness). `context.py:repair_tool_use_result_pairing` handles role-based messages (compaction output). `openai.py:_repair_orphaned_calls` handles flat Responses API items (post-normalization). OpenClaw only has one: `repairToolUseResultPairing` at the session-transcript level. The CUA architecture forces two because messages exist in two formats at different pipeline stages.

   **Concrete fix**: Add a comment in `_repair_orphaned_calls` referencing `context.py:repair_tool_use_result_pairing` as the role-based counterpart, and explain why both exist.

3. **No unit tests for `_normalize_messages_for_gpt54`** (Implementation Progress). This is the most complex function in the story (130 lines, 7+ code paths) and has zero direct test coverage. It's only tested implicitly via VM runs.

   **Concrete fix**: Add a `test_normalize_messages_for_gpt54.py` with cases for: text blocks, computer_call expansion, function_call expansion, tool_result conversion, stale empty-action handling, already-valid items passthrough, string content wrapping.

### OpenClaw Adapter Comparison (Requested Focus)

**Question**: Does the current implementation match OpenClaw's cross-model format adaptation pattern?

**Answer**: No — and this is intentional and acceptable. Here's why:

| Aspect | OpenClaw | US-OC-037 (CUA) |
|--------|----------|------------------|
| **Where format conversion happens** | `sanitizeSessionHistory()` — centralized, before any provider loop | `_normalize_messages_for_gpt54()` — inside the OpenAI loop's `predict_step()` |
| **What it converts** | Session messages (role-based, `{role, content}`) → sanitized messages for the target provider | Completion-format items (from compaction) → Responses API items for GPT 5.4 |
| **Scope** | All providers (Anthropic, Google, OpenAI) share a single pipeline with provider-specific passes | Per-loop: Anthropic loop has its own handling, OpenAI loop has its own |
| **Repair pattern** | `repairToolUseResultPairing()` runs on session messages (role-based) at one call site | Two implementations: `repair_tool_use_result_pairing()` for role-based (compaction), `_repair_orphaned_calls()` for Responses API items (openai.py) |

**Why the divergence is acceptable**:
1. CUA doesn't have a session-history sanitization layer — loops receive raw items
2. The Responses API format (flat items with `type` field) is fundamentally different from completion format (role-based messages with content arrays)
3. The compaction pipeline outputs role-based messages, so conversion _must_ happen somewhere before the Responses API call
4. OpenClaw doesn't have this problem because all its providers use the same message format (pi-agent-core's `AgentMessage`)

**What OpenClaw's adapter does NOT help with here**: OpenClaw's `sanitizeSessionHistory` is designed for provider-level differences within the same message format. US-OC-037's challenge is converting _between_ message formats (completion → Responses API). OpenClaw never faces this because it uses a unified message format across all providers. The `_normalize_messages_for_gpt54()` function is genuinely novel work with no OpenClaw counterpart.

### Future Work: computer-use-preview Regression (AC #7)

Regression testing with `computer-use-preview` revealed that this model also uses the Responses API and rejects `{"type": "text"}` content blocks — the same issue `_normalize_messages_for_gpt54` fixes for GPT 5.4. The normalization is currently gated behind `_is_gpt54(model)` and needs to be extended to all Responses API models. Error: `Invalid value: 'text'. Supported values are: 'input_text', 'input_image', 'output_text', ...` at `input[2].content[0].type`. This should be addressed in a future story by either:
1. Running `_normalize_messages_for_gpt54` for all models in the OpenAI loop, or
2. Centralizing message normalization upstream (aligns with US-OC-038).
